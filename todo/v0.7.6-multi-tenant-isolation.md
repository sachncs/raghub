# v0.7.6 — Multi-tenant DB isolation (all three strategies)

## Theme

Ship all three isolation strategies as first-class:
**row-level** (default, works on every backend),
**schema-per-tenant** (Postgres + pgvector), and
**database-per-tenant** (Postgres, generic connection routing).
Add per-tenant secrets with Fernet encryption. Add migration helpers
between strategies. Add tenant lifecycle CLI commands. This release
relies on `TenantResolver` from v0.7.3 and `PgVectorStore` from
v0.7.5.

This release has the largest security surface of any in the v0.7.x
series and requires an external security review sign-off as part of
the acceptance gate.

## Breaking changes (R4 — no shims, no aliases, no deprecation)

- New `IsolationStrategy` enum: `ROW_LEVEL | SCHEMA_PER_TENANT |
  DATABASE_PER_TENANT`. `Settings.isolation.strategy` selects the
  strategy at startup.
- `TenantContext` is now a first-class object propagated through
  every storage call. Any code that constructed a `VectorStore`
  directly without going through `TenantContext` must migrate.
- `raghub tenant list | create | delete` CLI commands added.
- `raghub migrate tenant-split --from … --to …` sub-command added.
- Per-tenant secrets (`tenant_secrets` table) introduced.
- Postgres RLS policies added; any Postgres user without
  `raghub_app` role loses access to `raghub_chunks`.

## Prerequisites

- `v0.7.5` is the current published release.

## Atomic items

69. **`IsolationStrategy` enum + `TenantContext` Protocol** —
    `raghub/tenants/isolation.py`:
    ```python
    class IsolationStrategy(StrEnum):
        ROW_LEVEL = "row_level"
        SCHEMA_PER_TENANT = "schema_per_tenant"
        DATABASE_PER_TENANT = "database_per_tenant"

    @dataclass(frozen=True, slots=True)
    class TenantContext:
        tenant_id: TenantId
        user_id: UserId | None
        is_admin: bool = False
        isolation: IsolationStrategy = IsolationStrategy.ROW_LEVEL
    ```
    `TenantContext` is propagated via `contextvars.ContextVar`
    so async code paths pick it up without explicit threading.

    Tests:
    - `test_tenant_context_propagates_through_async`
    - `test_tenant_context_required_for_strategies_other_than_row_level`
    - `test_tenant_context_immutable`

70. **Row-level isolation generalised** — every `VectorStore` query
    accepts an optional `tenant_id` and applies a WHERE clause
    `tenant_id = $1` (or equivalent). `MemoryStore` and
    `SqliteStore` add the column; `PgVectorStore` already has it
    from v0.7.5. The query is auto-injected when
    `TenantContext.tenant_id` is set; admin context bypasses the
    filter (`is_admin=True`).

    Tests:
    - `test_row_level_filter_applied_when_tenant_set`
    - `test_row_level_filter_bypassed_for_admin`
    - `test_row_level_isolation_cross_tenant_no_leak`

71. **Schema-per-tenant tier** — Postgres only. `raghub_postgres.py`
    in `raghub/tenants/postgres.py`:
    - On first access, create `tenant_<id>` schema and run
      `raghub migrate pgvector --dsn … --schema=tenant_<id>`.
    - On every connection acquisition, `SET search_path TO
      tenant_<id>, public`.
    - On tenant deletion, drop the schema (configurable; default
      `False` for safety — operator must pass `--force`).

    Tests:
    - `test_schema_per_tenant_creates_schema_on_first_access`
    - `test_schema_per_tenant_routes_search_path`
    - `test_schema_per_tenant_drop_schema_on_delete`

72. **Database-per-tenant tier** — Postgres only, generic
    connection-string-per-tenant router. `Tenants` registry
    (`raghub/tenants/registry.py`) maps `tenant_id` →
    `{"dsn": "postgresql://…", "vector_dim": N}`. `TenantRouter`
    opens a connection from a pool keyed by tenant.

    Tests:
    - `test_database_per_tenant_routes_dsn`
    - `test_database_per_tenant_pool_eviction`
    - `test_database_per_tenant_unknown_tenant_raises`

73. **`raghub migrate tenant-split --from … --to …`** — one command
    per direction:
    - `--from row_level --to schema_per_tenant`: for each tenant,
      create `tenant_<id>` schema, copy rows, drop originals from
      `public.raghub_chunks`, validate counts.
    - `--from schema_per_tenant --to database_per_tenant`: for
      each tenant, dump `tenant_<id>` schema, restore into a new
      database per the registry, validate counts.
    - `--from row_level --to database_per_tenant`: row-level →
      database-per-tenant in one step.

    Each direction is implemented as a separate helper. Each helper
    has its own test.

    Tests:
    - `test_migrate_row_level_to_schema_per_tenant`
    - `test_migrate_schema_per_tenant_to_database_per_tenant`
    - `test_migrate_validates_row_counts`
    - `test_migrate_rollback_on_failure`

74. **CLI: `raghub tenant list | create | delete`** —
    `raghub/cli_commands/__init__.py`:
    - `list` — prints `tenant_id`, `isolation_strategy`,
      `created_at`, `chunk_count`, `secrets_count`.
    - `create <tenant_id> --isolation=…` — registers the tenant in
      the registry; creates the schema or database depending on
      strategy.
    - `delete <tenant_id> [--force]` — removes the tenant; default
      refuses if any data exists; `--force` drops.

    Tests:
    - `test_cli_tenant_list`
    - `test_cli_tenant_create`
    - `test_cli_tenant_delete_refuses_with_data`
    - `test_cli_tenant_delete_force`

75. **Per-tenant secrets (Fernet-encrypted API keys)** —
    `raghub/tenants/secrets.py`:
    ```python
    class TenantSecrets(Protocol):
        def get(self, tenant_id: TenantId, key: str) -> str | None: ...
        def set(self, tenant_id: TenantId, key: str, value: str) -> None: ...
        def rotate(self, tenant_id: TenantId, key: str) -> str: ...
        def list_keys(self, tenant_id: TenantId) -> list[str]: ...
    ```
    Default impl: `SqliteTenantSecrets` using `cryptography.fernet`.
    Key rotation tested; tampering tested.

    Tests:
    - `test_tenant_secret_round_trip`
    - `test_tenant_secret_tampering_raises`
    - `test_tenant_secret_rotation_invalidates_old_value`
    - `test_tenant_secret_list_keys_returns_only_keys_not_values`

76. **Hard guarantee: missing tenant claim under
    `SCHEMA_PER_TENANT` / `DATABASE_PER_TENANT` raises
    `AuthorizationError` before any DB call** — middleware check in
    `raghub/api.py`. Verified by a test that times the
    `AuthorizationError` against the DB-call clock and asserts the
    error fires first.

    Tests:
    - `test_missing_tenant_claim_raises_authorization_error_before_db_call`
    - `test_missing_tenant_claim_under_row_level_succeeds`

77. **Audit log on every tenant-bound operation** — reuses
    `raghub/audit/__init__.py` from v0.7.3. New audit event
    `TENANT_BOUND_OPERATION` with fields `tenant_id`, `user_id`,
    `operation`, `isolation_strategy`, `timestamp`, `signature`.

    Tests:
    - `test_audit_records_tenant_bound_operation`
    - `test_audit_signature_verifies`

78. **Tenant-scoped migrations: `raghub migrate tenant --tenant
    <id>`** — runs the migration for a single tenant (e.g.
    schema creation, secret rotation). Used by the operator for
    incremental rollout.

    Tests:
    - `test_migrate_tenant_single`
    - `test_migrate_tenant_unknown_tenant_raises`

79. **Plugin registry: `register_isolation_strategy`** — new
    `PluginKind.ISOLATION_STRATEGY` and entry-point
    `group="raghub.isolation"`. Allows community isolation
    strategies (e.g. row-level with column-encryption) without
    shipping them.

    Tests:
    - `test_plugin_registry_isolation_strategy`

## Security review

This release is the largest security surface of any in the v0.7.x
series; the security artefact is
`docs/security/threat-models/v0.7.6-isolation.md`.

The threat model is mandatory and detailed. An external security
review sign-off is a release-blocking acceptance gate.

### Threat model

| Threat | Mitigation |
|---|---|
| **Cross-tenant data leakage via row-level filter bypass**: a code bug in any of the three stores allows a query to skip the `tenant_id` filter. | Property test `test_cross_tenant_no_leak` runs in CI on every push. The test seeds both tenants with distinguishable data and asserts that A's query never surfaces B's rows. |
| **Schema-per-tenant search_path escape**: a connection's `search_path` is set after acquisition; a concurrent modification of the path leaks across tenants. | `search_path` set inside the same transaction as the query; transaction-scoped. Property test asserts concurrent tenants never observe each other's data. |
| **Database-per-tenant pool confusion**: a worker thread holds a connection from tenant A's pool and uses it for tenant B's request. | `TenantRouter` keys connections by tenant id; the connection's session variables are reset on every acquisition; the `SET LOCAL` enforces `app.current_tenant_id` per request. Property test asserts no confusion. |
| **Missing tenant claim under schema-per-tenant / database-per-tenant**: a request without a tenant claim proceeds and reads `public` schema or the default database. | Hard middleware check raises `AuthorizationError` before any DB call. Test asserts the error fires before any DB query is logged. |
| **Tenant-id spoofing**: an attacker sets `X-Tenant-ID: <victim>` to read another tenant's data. | `TenantResolver` prefers the JWT claim over the header (v0.7.3). For storage routing, the `TenantContext` is constructed from the resolved claim, never from the request body. |
| **Per-tenant secret leakage via logs**: a Fernet-encrypted secret is accidentally logged in plaintext. | `RedactingTelemetry` already redacts keys named `*secret*`, `*key*`, `*password*`. CI test asserts no plaintext secret in logs. |
| **Tenant-deletion data leak**: deleting a tenant leaves their data in `public` schema (row-level) or in a leftover schema (schema-per-tenant). | Default `tenant delete` refuses if any data exists; `--force` drops; in schema-per-tenant, the schema is dropped; in database-per-tenant, the registry entry is removed and the database is marked for manual deletion. |
| **Backup of cross-tenant data via the audit log**: the audit log contains all tenants' operations; an attacker with read access to the audit DB infers activity. | Audit log access restricted to admin role; documented operator concern. |
| **Postgres RLS bypass via `BYPASSRLS`**: a role with `BYPASSRLS` attribute ignores RLS. | `raghub_app` role explicitly without `BYPASSRLS`; documented in the migration guide. |
| **Tenant-id length / format DoS**: an attacker submits a tenant id of 1 MB to exhaust the connection pool. | Tenant id validated against the strict regex from v0.7.3; oversized values rejected at submit time. |
| **Migration rollback failure**: a `tenant-split` migration fails partway through; tenants are left in a mixed state. | Migration runs in a transaction; rollback tested; explicit resume command for partial migrations. |
| **Cryptographic key compromise**: the Fernet key is leaked. | Key rotation API (already in v0.7.6); operator responsibility to rotate `RAGHUB_TENANT_SECRETS_KEY` regularly; documented. |

### Mitigations accepted

- Row-level, schema-per-tenant, and database-per-tenant tiers all
  backed by property tests.
- Hard middleware check for missing tenant claim.
- Fernet encryption for tenant secrets with rotation.
- Postgres RLS policies.
- Strict tenant-id validation.
- Transaction-scoped `search_path`.
- Pool keyed by tenant id.

### Out-of-scope

- Backup of cross-tenant data: v0.7.8.
- Feedback tenant isolation: v0.7.7.
