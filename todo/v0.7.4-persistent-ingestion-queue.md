# v0.7.4 — Persistent ingestion queue

## Theme

Replace the in-process threadpool `Batch` with a persistent,
SQLite-backed job queue. Add a `Worker` runtime, a job state machine,
idempotency via content hash, and backpressure. Wire `RAG.ingest_async`
to the new queue. This release also introduces the `tenant_id` column
on every job, even though routing on `tenant_id` is the v0.7.6 release.

## Breaking changes (R4 — no shims, no aliases, no deprecation)

- `Resumable(Batch)` is replaced by `PersistentQueue` (Protocol) +
  `SqliteQueue` (default implementation).
- `Job` gains the fields `attempts: int`, `last_error: str | None`,
  `next_run_at: datetime`, `worker_id: str | None`,
  `tenant_id: str | None`. Old consumers reading the previous
  shape must migrate.
- `RAG.ingest_async` returns the **job id** instead of the previous
  background-handle string. Any code that compared the return value
  to a `Batch`-specific handle must migrate.
- CLI sub-commands added: `raghub queue list | run | retry | purge`.
- A new SQLite table `raghub_queue` is created automatically; if the
  operator has an existing `JobStore` SQLite file from a v0.7.x
  release, the table is added in place. No data migration is
  provided because R4 forbids shims — old jobs in the previous
  table are not migrated.

## Prerequisites

- `v0.7.3` is the current published release.

    Update `Job` to a frozen dataclass (already done in v0.7.2 item
    44 — verify). The frozen dataclass carries field-level
    validators: `tenant_id` validated against the same regex as
    `TenantResolver`; `payload` validated as JSON-serialisable.

    Tests:

    - `test_job_payload_must_be_json_serialisable`

54. **`PersistentQueue` Protocol** — `raghub/jobs/queue.py`. Define:
    ```python
    class PersistentQueue(Protocol):
        async def submit(self, job: Job) -> str: ...
        async def claim(self, worker_id: str, lease_seconds: int) -> Job | None: ...
        async def ack(self, job_id: str) -> None: ...
        async def nack(self, job_id: str, error: str) -> None: ...
        async def retry(self, job_id: str, delay_seconds: int) -> None: ...
        async def dead_letter(self, job_id: str) -> None: ...
        async def purge(self, status: JobStatus | None = None) -> int: ...
        async def list(self, status: JobStatus | None = None, limit: int = 100) -> list[Job]: ...
        async def stats(self) -> QueueStats: ...
    ```

    Protocol conformance test that any concrete implementation must
    pass.

55. **`SqliteQueue` implementation** — `raghub/jobs/sqlite.py`.
    Schema:
    ```sql
    CREATE TABLE IF NOT EXISTS raghub_queue (
        id TEXT PRIMARY KEY,
        kind TEXT NOT NULL,
        payload TEXT NOT NULL,             -- JSON
        status TEXT NOT NULL,              -- pending|running|succeeded|failed|dead
        attempts INTEGER NOT NULL DEFAULT 0,
        max_attempts INTEGER NOT NULL DEFAULT 3,
        last_error TEXT,
        next_run_at TEXT NOT NULL,         -- ISO-8601
        worker_id TEXT,
        tenant_id TEXT,
        created_at TEXT NOT NULL,
        updated_at TEXT NOT NULL
    );
    CREATE INDEX IF NOT EXISTS raghub_queue_status_next_run
        ON raghub_queue (status, next_run_at);
    CREATE INDEX IF NOT EXISTS raghub_queue_tenant_id
        ON raghub_queue (tenant_id);
    ```

    Use `aiosqlite` (already in `[auth]` extra). All queries
    parameterised.

    Tests:
    - `test_sqlite_queue_submit_claim_ack`
    - `test_sqlite_queue_claim_returns_none_when_empty`
    - `test_sqlite_queue_nack_increments_attempts`
    - `test_sqlite_queue_dead_letter_after_max_attempts`
    - `test_sqlite_queue_purge_by_status`
    - `test_sqlite_queue_concurrent_workers`

56. **`Worker(concurrency, max_retries, retry_backoff, dead_letter)`**
    — `raghub/jobs/worker.py`. Implements:
    - Lease-based claiming (`SELECT … FOR UPDATE`-like semantics via
      SQLite transaction).
    - Per-attempt timeout (`max_wall_seconds`).
    - Exponential backoff: `delay_seconds = base *
      (2 ** (attempts - 1))`, capped at `max_delay_seconds`.
    - Dead-letter routing after `max_attempts` exhausted.
    - Worker id format: `worker-<hostname>-<pid>-<uuid4[:8]>`.

    Tests:
    - `test_worker_processes_pending_job`
    - `test_worker_retries_on_failure`
    - `test_worker_dead_letters_after_max_attempts`
    - `test_worker_backoff_caps_at_max_delay`
    - `test_worker_concurrency_limit_respected`

57. **Job state machine: `pending → running → succeeded | failed |
    dead`** — `raghub/jobs/state_machine.py`. Each transition is
    guarded by a transition table. Illegal transitions raise
    `JobStateError`.

    Transition table:
    | From | To | Allowed |
    |---|---|---|
    | pending | running | yes |
    | running | succeeded | yes |
    | running | failed | yes (increments attempts, sets next_run_at) |
    | running | dead | yes (when attempts >= max_attempts) |
    | pending | dead | yes (manual dead_letter call) |
    | succeeded | * | no |
    | dead | * | no |
    | failed | pending | yes (on retry() call, resets status, sets next_run_at) |

    Property test: `test_state_machine_no_illegal_transitions`
    (Hypothesis: any random sequence of transition attempts must
    either succeed or raise `JobStateError`, never produce an
    inconsistent state).

58. **SHA-256 content-hash idempotency** — `raghub/ingest.py` and
    `raghub/rag.py`. Before submitting an ingest job, compute
    `sha256(payload + tenant_id or "")`; if a job with the same
    hash and `kind="ingest"` is in any terminal state
    (`succeeded`), return the existing job id instead of submitting
    a new job. This applies to `RAG.ingest` and `RAG.ingest_async`.

    Tests:
    - `test_idempotent_ingest_returns_existing_job_id`
    - `test_idempotent_ingest_does_not_double_submit`
    - `test_idempotent_ingest_respects_force_flag`

59. **`max_inflight` backpressure → `QueueSaturatedError`** —
    `raghub/jobs/sqlite.py`. `SqliteQueue.submit` checks
    `count(status='pending') + count(status='running')` against
    `Settings.queue.max_inflight`. Over-limit raises
    `QueueSaturatedError` (new exception class added to
    `raghub/errors.py`).

    Tests:
    - `test_queue_raises_saturated_when_over_max_inflight`
    - `test_queue_accepts_after_drain`
    - `test_queue_max_inflight_configurable`

60. **CLI: `raghub queue list | run | retry | purge`** —
    `raghub/cli_commands/__init__.py`. Each subcommand:

    - `list` — shows `id`, `kind`, `status`, `attempts`, `next_run_at`,
      `tenant_id`. Filter flags: `--status`, `--tenant`, `--limit`.
    - `run` — starts a `Worker` reading from `Settings.queue`.
      Flags: `--workers`, `--max-attempts`, `--max-wall-seconds`,
      `--lease-seconds`.
    - `retry <job_id>` — moves a `failed` or `dead` job back to
      `pending` with a configurable delay.
    - `purge` — deletes jobs by status; default `--status=succeeded`
      older than `--older-than-days=7`.

    Tests:

    - `test_cli_queue_run_starts_worker`
    - `test_cli_queue_retry_resets_state`
    - `test_cli_queue_purge_default`

## Security review

This release introduces a persistent queue with multi-tenant fields
and a worker runtime; the security artefact is
`docs/security/threat-models/v0.7.4-queue.md`.

### Threat model

| Threat | Mitigation |
|---|---|
| **Job-poisoning**: an attacker submits a job whose `payload` is a JSON document shaped like an ingest call but with extra fields designed to confuse the worker (e.g. a `__class__` field that triggers `pickle` deserialisation downstream). | Payload validator at submit time: `payload` must be JSON-serialisable; extra unknown fields are dropped or rejected (decided by a strict schema per `kind`). |
| **Tenant-id forgery**: an attacker submits a job with `tenant_id="victim"` to cause work to land in the victim's tenant scope. | `tenant_id` is taken from `TenantResolver.resolve()` at submit time; the caller cannot override it. If `tenant_id` is missing, the job is rejected unless the caller is admin. |
| **Worker privilege escalation**: a worker running as a low-privilege user exploits the queue to gain higher privileges. | Worker process runs with the same privileges as the caller; the queue does not change the security context. `worker_id` is recorded for every transition. |
| **Queue DoS via backpressure bypass**: an attacker submits jobs faster than the worker drains, exhausting disk space. | `max_inflight` raises `QueueSaturatedError` at submit; jobs rejected; HTTP 503 surfaced. Disk-space monitor (operator concern) referenced in the threat model. |
| **Replay attack**: a `succeeded` job's id is replayed by an attacker to re-trigger work. | Job ids are UUIDv4 (cryptographically random); the replayed id is not the same job. Idempotency layer additionally checks content hash. |
| **Dead-letter leak**: a job in `dead` state carries `last_error` which may contain credentials or secrets. | `last_error` is sanitised: stack traces stripped of `Authorization`, `api_key`, `secret` substrings before persistence. |
| **SQL injection**: a `kind` or `status` value contains SQL fragments. | All SQL parameterised; values bound via `?`. |
| **Cross-tenant leak via list**: `raghub queue list` shows another tenant's job ids. | Default `list` filters by the caller's `tenant_id`; admin role required to see across tenants; tests assert. |

### Mitigations accepted

- Payload validation at submit.
- `tenant_id` from `TenantResolver`, never from caller input.
- Backpressure via `max_inflight`.
- Job id is UUIDv4.
- `last_error` sanitisation.
- Parameterised SQL.
- Default `list` filters by tenant.

### Out-of-scope

- Per-tenant queue worker pools: deferred (a single worker serves
  all tenants; per-tenant routing on the queue is the v0.7.6
  release).
- Backup of the queue table: v0.7.8 (the queue table is one of
  the files included in the backup tarball).
